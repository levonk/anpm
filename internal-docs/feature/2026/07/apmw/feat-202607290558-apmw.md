# Product Requirements Document (PRD)

## Introduction / Overview

- **Feature name:** apmw (All Package Manager Wrapper)
- **Summary:** apmw is a Rust-based tool that abstracts every package installer into one intelligent surface. It detects the correct package manager for the current project, adds tools and dependencies with install-on-use semantics (distinguishing runtime vs. development/build-time dependencies), maps within-ecosystem alternatives to canonical runners (pip to uv within Python, npm/yarn/bun to pnpm within Node — never across ecosystems), scans PATH before installing, resolves versions intelligently with a default minimum-release-age supply-chain defense, reads governance rules (prefer/force/block/eject) from the levonk-packages governance spec rather than reinventing them, collects anonymized tool-usage telemetry, supports container packages (docker/podman images), creates historyless clones with AST indexing, runs security scanning before install, keeps an audit log, runs as a tokio daemon with background agents, notifies AI agents where to find package docs, exposes AI agent hooks/MCP/Skills, and ships as a multi-ecosystem release from one source.
- **Context:**
  - **Who:** Developers and AI agents (Claude Code, Codex, OpenCode) who interact with package managers across multiple ecosystems (Node, Python, Rust, Go, Debian, Brew, Nix, Snap, Yum, and more).
  - **Problem:** Every package manager has its own CLI, its own security posture, its own version resolution rules, and its own ad-hoc runner. Developers waste time context-switching between `pip`, `npm`, `cargo`, `brew`, `apt`, `nix`, and `go install`. AI agents have no enforced path for adding dependencies — they call whatever package manager they guess, bypassing security scanning and audit logging.
  - **Solution:** One tool that detects the right package manager, maps to canonical ecosystems, scans before installing, resolves versions intelligently, clones historylessly with AST indexing, and forces AI agents through a single install-on-use hook.
  - **Background:** The concept originated in the 2ndbrain vault note "APMW Tool Idea" (Obsidian, not in any git repo) and was refined in the 38KB research document "All Package Manager Wrapper Tool Landscape" containing a Package Manager Hierarchy (OS Wrapper, OS-Level, Virtualization/Container, Language, App levels), Table 1 (project-detection attributes for 20+ package managers and build systems), and Table 2 (apmw command to per-package-manager command mapping with 200+ references). The PRD generation handoff document is at `~/p/gh/levonk/levonk-packages/.agents/handoffs/2026/07/202607290407-apmw-prd-generation.md`.

## Goals

1. **Detect** the correct package manager for any project by scanning lockfiles, config files, and directory markers — delegating to the project-detection/project-adopter/project-configuration skills' logic. The CLI must allow the user to override the detected manager with `--manager <name>` (e.g., `--manager pnpm`, `--manager uv`, `--manager cargo`).
2. **Add** tools and dependencies with install-on-use semantics, routing through devbox + rtk when no impossible barriers exist. The primary command is `apmw add` (not `install`), following the modern convention adopted by pnpm, yarn, uv, poetry, and cargo. apmw must distinguish **runtime** dependencies from **development/build-time** dependencies via a `--dev` flag (mirroring `pnpm add -D`, `cargo add --dev`, `pip install --group dev`).
3. **Map within-ecosystem alternatives** to canonical runners — never across ecosystems. Within Python: pip to uv, pipx to uvx. Within Node: npm/yarn/bun/yarn2 to pnpm, npx/bunx/yarn dlx to `pnpm dlx`. The canonical ad-hoc runner per ecosystem is resolved via `cli-tool-discovery.sh --runner <ecosystem>`. apmw must NOT map a Python runner to a Node runner or vice versa.
4. **Scan PATH** before installing to avoid duplicate installations.
5. **Suggest** better alternatives for the current use case (e.g., suggest uv when the user runs pip — within the same ecosystem).
6. **Install missing tools** itself when needed, using the detected (or `--manager`-overridden) package manager.
7. **Resolve versions** intelligently: pinned version if locked; latest compatible with engine; latest if unspecified; latest minor if only major specified. As a supply-chain defense, the default behavior requires a dependency to be at least **2 days old** (published >= 2 days ago) before auto-pulling that version. This is overrideable via `--min-age-days <N>` (set to 0 to disable) or `--allow-new`.
8. **Read governance rules** (prefer/force/block/eject) from the levonk-packages governance spec at `https://github.com/levonk/levonk-packages` (see `docs/SPEC.md`) rather than reinventing the policy format. apmw's tool config must allow per-tool governance settings that map to the levonk-packages governance types.
9. **Create historyless/branchless/tagless clones** of any package with `--depth 1 --single-branch --no-tags`, with indexed-AST search tools loaded and indexes created (CodeGraph/Graphify/GitNexus per the indexed-ast-tools decision tree). Add a local `.gitignore` so indexes, devbox.json, and AGENTS.md do not get pushed upstream.
10. **Run security scanning before install** (two-phase: scan all then install all), with option to update security databases first. Telemetry off for third-party packages being installed; on or neutral for levonk-owned packages.
11. **Collect anonymized tool-usage telemetry** so we understand how apmw is used: whether the terminal is interactive/TUI/login, which commands are run, which package managers are invoked, success/failure rates. NO personal identifiers, NO package names, NO file paths — only categorical usage data. Telemetry is opt-out via `--no-telemetry` or config.
12. **Keep an audit log** in `${XDG_CACHE_HOME:-$HOME/.cache}/apmw/` recording: when, what was requested, what was done, whether the terminal was login/interactive, caller program, and which tools were used.
13. **Run as a Rust daemon** (tokio "full") with background agents doing clone/scan/index in the background; CLI reports status of clone/security-scan/add/indexing.
14. **Support container packages** — detect and manage docker/podman images and container packages (pull, scan, list) alongside traditional package managers. Container packages live at the Virtualization/Container hierarchy level.
15. **Notify the user's AI agent** where to find docs for an installed package.
16. **Expose AI agent coding hooks, an MCP, and Skills** that force AI agents through apmw's install-on-use hook for adding dependencies and running tools.
17. **Ship as multi-ecosystem release** (npm/pnpm, PyPI/uv, brew, nix, devbox, apt, winget, apk, deb, rpm) from one source.

## User Stories

1. **As a developer**, I want to run `apmw add <package>` in any project directory and have apmw detect the right package manager, resolve the version, scan for security issues, and add the dependency — so I do not have to remember which package manager this project uses.

2. **As a developer**, I want to run `apmw add <package> --dev` to add a development/build-time dependency (not shipped to production) — so I keep runtime and build dependency sets separate, mirroring `pnpm add -D`, `cargo add --dev`, and `pip install --group dev`.

3. **As a developer**, I want to override apmw's auto-detected package manager with `--manager <name>` (e.g., `apmw add foo --manager pnpm`) — so I can force a specific package manager when the auto-detection picks the wrong one or when I have a preference.

4. **As a developer**, I want apmw to scan my PATH before installing a tool and skip the installation if the tool is already available — so I avoid duplicate installations and wasted time.

5. **As a developer**, I want apmw to suggest better alternatives within the same ecosystem (e.g., uv instead of pip, pnpm instead of npm — never pip instead of npm) — so I adopt the best tool for each ecosystem without researching manually.

6. **As a developer**, I want apmw to create a historyless clone of any package with AST indexing enabled — so I can search the code structurally without downloading git history or polluting the upstream repo with index files.

7. **As a developer**, I want apmw to run security scanning before installing anything — so I do not install packages with known vulnerabilities.

8. **As a developer**, I want apmw to refuse to auto-pull a dependency version published less than 2 days ago by default (overrideable with `--min-age-days 0` or `--allow-new`) — so I am protected against supply-chain attacks that ship malicious versions and pull them before the community can audit them.

9. **As a developer**, I want apmw to read governance rules (prefer/force/block/eject) from the levonk-packages governance spec so I can configure per-tool governance (e.g., "force pnpm over npm", "block pip") without apmw reinventing the policy format.

10. **As a developer**, I want apmw to support container packages — pulling, scanning, and listing docker/podman images alongside traditional package managers — so I can manage container dependencies the same way I manage library dependencies.

11. **As an AI agent** (Claude Code, Codex, OpenCode), I want apmw to expose an MCP server and installable Skills — so I can route all dependency additions and tool invocations through apmw's install-on-use hook without guessing the package manager.

12. **As an AI agent**, I want apmw to notify me where to find the docs for an installed package — so I can read the package's documentation before using its APIs.

13. **As a developer**, I want apmw to run as a daemon with background agents handling clone/scan/index — so long-running operations do not block my terminal.

14. **As a developer**, I want apmw to keep an audit log of every add/detect/clone operation — so I can review what was installed, when, and by which tool.

15. **As a DevOps engineer**, I want apmw to ship as multi-ecosystem packages (npm, PyPI, brew, nix, apt, winget, apk, deb, rpm) — so I can install it on any platform through the native package manager.

16. **As a developer**, I want apmw to resolve versions intelligently (pinned, engine-compatible, latest, latest-minor) — so I get the right version without manually specifying it every time.

17. **As an AI agent**, I want apmw to output in TOON format with minimal schemas and no interactive prompts — so I can parse the output efficiently and act on it without wasting tokens.

18. **As a maintainer**, I want apmw to collect anonymized usage telemetry (terminal type, commands run, package managers used, success/failure — no personal identifiers, no package names, no paths) — so I can understand how the tool is used and improve it. I can opt out via `--no-telemetry` or config.

## Functional Requirements

### FR-1: Package Manager Detection

- **FR-1.1:** apmw must detect the package manager for the current project by scanning for lockfiles and config files (package.json, Cargo.toml, pyproject.toml, go.mod, Gemfile, pubspec.yaml, Dockerfile, Chart.yaml, Vagrantfile, WORKSPACE, BUILD, etc.).
- **FR-1.2:** Detection logic must delegate to the project-detection, project-adopter, and project-configuration skills' attribute-based detection. The 2ndbrain research Table 1 (at `~/p/gh/lrepo52/2ndbrain/2ndbrain/Work/01 OandO/Self Improvement/Want To Build/Digital/All Package Manager Wrapper/All Package Manager Wrapper Tool Landscape.md`) defines the detection attributes for 20+ package managers and build systems.
- **FR-1.3:** apmw must support detecting package managers and build systems across every level of the Package Manager Hierarchy defined in the 2ndbrain research document:
  - **OS Wrapper Level:** mise, brew (CLI: taproom, forage), nix
  - **OS-Level:** apt, dnf, pacman, nix (Linux); winget (Windows); brew (macOS)
  - **Virtualization / Container Level:** docker (Dockerfile, docker-compose.yml, docker-compose.*.yml), packer (*.pkr.hcl, *.json), docker hub image references
  - **Language Level:** npm, yarn, pnpm, bun (node); cargo (rust); pip, uv, poetry, pipenv, pdm, conda (python); gem (ruby); go mod (go); maven, gradle, sbt, ant (jvm); flutter, dart (dart); dotnet/nuget (.NET)
  - **App Level:** helm (k8s, Chart.yaml), flatpak, snap, devbox (devbox.json), vagrant (Vagrantfile)
  - **Build Systems:** bazel (WORKSPACE, BUILD), buck (BUCK), pants (BUILD, pants.toml), cmake, xcode, cocoapods, carthage, spm
- **FR-1.4:** Detection must return the detected manager, the confidence level, the hierarchy level, and the evidence (which files triggered the detection).
- **FR-1.5:** When multiple managers are detected at different hierarchy levels (e.g., a Dockerfile at the Virtualization Level and a package.json at the Language Level), apmw must report all detected managers and select the most specific one for the requested operation, with the hierarchy level recorded in the audit log.
- **FR-1.6:** The CLI must accept `--manager <name>` (alias `--use <name>`) to override auto-detection and force a specific package manager for the current command. Valid values include: `pnpm`, `npm`, `yarn`, `bun`, `uv`, `pip`, `poetry`, `pipenv`, `pdm`, `conda`, `cargo`, `go`, `gem`, `brew`, `nix`, `devbox`, `apt`, `dnf`, `pacman`, `winget`, `snap`, `flatpak`, `helm`, `docker`, `podman`, `maven`, `gradle`, `sbt`, `dotnet`. When `--manager` is passed, detection is skipped and the specified manager is used directly. The override is recorded in the audit log.

### FR-2: Ecosystem Mapping (Within-Ecosystem Only)

- **FR-2.1:** apmw must map **within-ecosystem** alternatives to canonical runners — never across ecosystems. A Python runner maps to a Python runner; a Node runner maps to a Node runner. Cross-ecosystem mapping (e.g., mapping a Python `uvx` to a Node `pnpm dlx`) is explicitly forbidden.
  - **Python ecosystem:** pip to uv, pipx to uvx, poetry/pipenv/pdm/conda remain as-is (no forced mapping)
  - **Node ecosystem:** npm/yarn/bun/yarn2 to pnpm, npx/bunx/`yarn dlx` to `pnpm dlx`
  - **Rust ecosystem:** cargo remains canonical (no within-ecosystem alternative)
  - **Go ecosystem:** `go install` remains canonical
  - The canonical ad-hoc runner per ecosystem is resolved via `cli-tool-discovery.sh --runner <ecosystem>` (python, node, rust, go)
- **FR-2.2:** When the user requests an add via a non-canonical manager within an ecosystem (e.g., `pip add`), apmw must suggest the canonical within-ecosystem alternative (e.g., `uv add`) and offer to use it. apmw must NOT suggest a runner from a different ecosystem.
- **FR-2.3:** The 2ndbrain research Table 2 (same file as FR-1.2) defines the apmw command to per-package-manager command mapping with 200+ references. apmw must implement this mapping table. The mapping table is per-ecosystem — each ecosystem's commands map within that ecosystem only.

### FR-3: PATH Scanning

- **FR-3.1:** Before installing any tool, apmw must scan common PATH destinations to check if the tool is already installed.
- **FR-3.2:** PATH scanning must use the `cli-tool-discovery.sh` resolution flow: devbox-aware resolution (check `DEVBOX_SHELL` env first), then wrapper detection (mise, flox, direnv, nix), then 30+ standard PATH locations, then repo-root fallback dirs (`$REPO_ROOT/bin`, `scripts/`, `.local/bin`).
- **FR-3.3:** If the tool is found, apmw must report the path and skip installation.

### FR-4: Version Resolution

- **FR-4.1:** apmw must resolve versions using this priority:
  1. Pinned version if locked (from lockfile)
  2. Latest version compatible with the engine in use (e.g., Node version, mobile API tag)
  3. Latest if unspecified
  4. Latest minor if only a major version is specified
- **FR-4.2:** Version resolution must respect engine constraints from the project's config (e.g., `engines` field in package.json, `python-requires` in setup.py, `rust-version` in Cargo.toml).
- **FR-4.3 (Supply-Chain Defense — Minimum Release Age):** By default, apmw must refuse to auto-pull a dependency version published less than **2 days ago**. If the resolved version was published < 2 days ago, apmw must fall back to the most recent version that is >= 2 days old and compatible with the engine constraints. If no such version exists, apmw must error with a clear message explaining the supply-chain defense and how to override.
- **FR-4.4:** The minimum release age is configurable:
  - CLI: `--min-age-days <N>` (set to 0 to disable the check entirely)
  - CLI: `--allow-new` (shorthand for `--min-age-days 0`)
  - Config file: `min_age_days = 2` (default)
  - Env var: `APMW_MIN_AGE_DAYS`
- **FR-4.5:** The minimum-age check applies only to auto-resolved versions (priority 3 and 4 above). Pinned versions (priority 1) and engine-compatible versions (priority 2) bypass the age check — the user explicitly locked or constrained those.

### FR-5: Security Scanning (Two-Phase)

- **FR-5.1:** apmw must run security scanning BEFORE install, following the two-phase pattern from `executable_skill-install.sh`: scan all packages first, then install all packages.
- **FR-5.2:** Scanners must be loaded as plugins following the scanner contract:
  - `<name>_available` — can this scanner run?
  - `<name>_ensure` — prepare/install the scanner
  - `<name>_scan DIR` — scan a local directory, return 0=safe/1=risky/2=error
- **FR-5.3:** Risk aggregation must use OR semantics: if ANY scanner reports risky (return 1), the package is treated as risky. Scanner errors (return 2) are incomplete-scan warnings, not risk findings.
- **FR-5.4:** apmw must support `--on-risk` modes: `prompt` (ask in interactive TTY, error if not), `error` (abort immediately), `warn` (print warning, install anyway), `skip` (skip the risky package, continue).
- **FR-5.5:** apmw must support `--update-security-db` to refresh security databases before scanning.
- **FR-5.6:** Telemetry policy for third-party packages: telemetry off for third-party packages; on or neutral for levonk-owned packages. This mirrors the `executable_skill-install.sh` telemetry policy (lines 73-76). This is distinct from the apmw tool's own anonymized usage telemetry (FR-5.8).
- **FR-5.7:** Security posture must mirror the `npmrc.tmpl` settings: `audit=true`, `audit-level=high`, `engine-strict=true`, `frozen-lockfile=true`, `save-exact=true`, `provenance=true`.

### FR-5.5: Add Command — Runtime vs. Development Dependencies

- **FR-5.5.1:** The primary install command is `apmw add <package>` (not `apmw install`), following the modern convention adopted by pnpm (`pnpm add`), yarn (`yarn add`), uv (`uv add`), poetry (`poetry add`), and cargo (`cargo add`).
- **FR-5.5.2:** apmw must distinguish **runtime** dependencies from **development/build-time** dependencies via a `--dev` flag:
  - `apmw add <package>` — adds a runtime dependency
  - `apmw add <package> --dev` — adds a development/build-time dependency
  - The mapping to each package manager's dev-dependency mechanism: pnpm/yarn/bun (`-D` / `--dev`), cargo (`--dev`), npm (`--save-dev`), pip/uv (`--group dev` or `--dev`), poetry (`--group dev`), pipenv (`--dev`), pdm (`--dev`), conda (`--dev`), go (separate `tools.go` or `go.mod` toolchain block), gem (`--development`), maven/gradle/sbt (scope `test` or `provided`), dotnet (`--package-directory`).
- **FR-5.5.3:** The 2ndbrain research Table 2 maps `apmw add` and `apmw add --dev` to the equivalent command in each package manager. apmw must implement this mapping.
- **FR-5.5.4:** `apmw add` must respect the `--manager <name>` override (FR-1.6), the version resolution rules (FR-4), the security scanning two-phase pattern (FR-5), and the minimum release age (FR-4.3).

### FR-5.6: Governance Rules (from levonk-packages)

- **FR-5.6.1:** apmw must read governance rules from the levonk-packages governance spec at `https://github.com/levonk/levonk-packages` (canonical spec: `docs/SPEC.md`). apmw must NOT reinvent the policy format.
- **FR-5.6.2:** apmw must support the four governance types defined in the levonk-packages spec:
  - **`prefer-*`** — soft guidance: warn when the disfavored tool is used, delegate to the preferred tool if installed, do not remove or block the disfavored tool
  - **`eject-*`** — enforcement engine: remove the disfavored tool if possible, block future installation, shadow the binary with a wrapper
  - **`force-*`** — strict replacement: depends on `eject-*`, installs the preferred tool, replaces the disfavored tool with a wrapper that delegates to the preferred tool
  - **`block-*`** — complete prohibition: depends on `eject-*`, does not install a replacement, replaces the disfavored tool with a wrapper that exits with an error
- **FR-5.6.3:** apmw's tool config (TOML, XDG-compliant) must allow per-tool governance settings that map to these governance types. Example:
  ```toml
  [governance.node]
  npm = "force-pnpm"      # force pnpm over npm
  yarn = "prefer-pnpm"   # prefer pnpm over yarn (soft)
  bun = "prefer-pnpm"    # prefer pnpm over bun (soft)

  [governance.python]
  pip = "force-uv"       # force uv over pip
  pipx = "prefer-uvx"    # prefer uvx over pipx (soft)

  [governance.containers]
  docker = "prefer-podman"  # prefer podman over docker (soft)
  ```
- **FR-5.6.4:** apmw must also support the `devbox-rtk-*` integrated package naming convention (`devbox-rtk-{ecosystem}-{preferred-tool}-{governance-type}`) from the levonk-packages spec, so governance rules are compatible with the existing devbox-rtk package ecosystem.
- **FR-5.6.5:** When a governance rule is `force-*` or `block-*` and the disfavored tool is invoked, apmw must intercept the invocation and route through the preferred tool (force) or error out (block), matching the levonk-packages wrapper behavior.

### FR-5.7: Container Package Support

- **FR-5.7.1:** apmw must detect and manage container packages (docker/podman images) alongside traditional package managers. Container packages live at the Virtualization/Container hierarchy level (FR-1.3).
- **FR-5.7.2:** apmw must support the following container package operations:
  - `apmw add <image>` — pull a container image (maps to `docker pull` / `podman pull`)
  - `apmw add <image> --dev` — pull a container image for development use only
  - `apmw scan <image>` — run security scanning on a container image (via `trivy`, `grype`, or `docker scout`)
  - `apmw list --manager docker` — list locally pulled container images
  - `apmw detect` — detect container usage from `Dockerfile`, `docker-compose.yml`, `docker-compose.*.yml`, `Containerfile`, `podman` files
- **FR-5.7.3:** Container image security scanning must use the same two-phase scan-all-then-install-all pattern (FR-5.1) and the same scanner plugin contract (FR-5.2).
- **FR-5.7.4:** apmw must support governance rules for container tools (e.g., `prefer-podman` over `docker`) per FR-5.6.
- **FR-5.7.5:** apmw must support `docker-compose` / `docker compose` as a container orchestration package manager (detected from `docker-compose.yml` / `compose.yaml`).

### FR-5.8: Anonymized Tool-Usage Telemetry

- **FR-5.8.1:** apmw must collect anonymized usage telemetry to understand how the tool is used. Telemetry data includes ONLY:
  - Terminal type: interactive, TUI, login, non-interactive (categorical, no content)
  - Commands run: `add`, `detect`, `scan`, `clone`, `status`, `list` (command name only, no arguments)
  - Package managers used: `pnpm`, `uv`, `cargo`, `brew`, etc. (manager name only, no package names)
  - Success/failure: boolean + error category (e.g., "security_scan_failed", "version_not_found")
  - Timing: duration of the operation in milliseconds (no timestamps)
  - apmw version
- **FR-5.8.2:** Telemetry must NOT include: package names, file paths, URLs, user identifiers, machine identifiers, IP addresses, environment variable values, or any content from the user's project. Only categorical usage data.
- **FR-5.8.3:** Telemetry is opt-out:
  - CLI: `--no-telemetry` (per-invocation)
  - Config: `telemetry = false` (default true)
  - Env var: `APMW_NO_TELEMETRY=1`
- **FR-5.8.4:** Telemetry is sent to a levonk-owned endpoint (configurable). The endpoint URL is in the config. If the endpoint is unreachable, telemetry is silently dropped (never blocks the user's operation).
- **FR-5.8.5:** This is distinct from the third-party package telemetry policy (FR-5.6): third-party packages being installed have telemetry OFF; the apmw tool itself has telemetry ON (anonymized, opt-out).

### FR-6: Historyless Clone with AST Indexing

- **FR-6.1:** apmw must create historyless, branchless, tagless clones using `git clone --depth 1 --single-branch --no-tags`.
- **FR-6.2:** After cloning, apmw must add a local `.gitignore` that excludes: AST index files, `devbox.json`, `AGENTS.md` — so these do not get pushed upstream.
- **FR-6.3:** apmw must load the appropriate indexed-AST search tool and create indexes, following the indexed-ast-tools decision tree:
  1. Project < 20 files? Skip indexing (agent can read everything directly).
  2. Need to link non-code knowledge (PDFs, docs, video, images) to code? Use Graphify (MIT, multimodal).
  3. Work across multiple repos/services? Use GitNexus (PolyForm Noncommercial — procure commercial license for business use).
  4. Need zero-maintenance + dynamic dispatch tracing? Use CodeGraph (MIT, auto-sync, single tool) — **default**.
  5. Power-user structural queries on a single repo? Use GitNexus (17 specialized MCP tools).
- **FR-6.4:** CodeGraph is the default for single-project zero-maintenance workflows.

### FR-7: Audit Log

- **FR-7.1:** apmw must keep an audit log in `${XDG_CACHE_HOME:-$HOME/.cache}/apmw/log/YYYY/MM/YYYYMMDDHHmmapmw.jsonl`.
- **FR-7.2:** Each log entry must record: timestamp (when), what was requested, what was done, whether the terminal was login/interactive, the caller program (if any), and which tools were used to install/run.
- **FR-7.3:** The audit log must be append-only with configurable retention period (per ADR-20260607001 section 34).
- **FR-7.4:** apmw must support an export command for external analysis of the audit log.

### FR-8: Daemon + CLI Service Model

- **FR-8.1:** apmw must run as a long-running Rust daemon (tokio "full") for background jobs (clone, scan, index).
- **FR-8.2:** The CLI is a thin client over a local socket that communicates with the daemon.
- **FR-8.3:** apmw must support `--daemon` (pre-launch daemon in background and wait for jobs), `--no-daemon` (force synchronous in-process operation), `--list-jobs` (show background job status, returns job ID immediately), `--cancel-job <id>` (cancel specific background jobs).
- **FR-8.4:** Auto-spawn daemon on first async operation (no flag required).
- **FR-8.5:** If daemon mode is not supported on the current platform, fall back to synchronous processing with a clear error message. Suggest alternatives if `--daemon` is used. Allow a config variable to override this noisy behavior for unsupported platforms.
- **FR-8.6:** This follows ADR-20260607001 section 13 exactly.

### FR-9: AXI Agent Mode

- **FR-9.1:** Agent mode is the DEFAULT (per ADR-20260607001 sections 36-45). No flags required.
- **FR-9.2:** Human mode triggered via `--human` flag, `--interactive` flag, TUI mode, or auto-detection when TTY is present and no agent session is detected.
- **FR-9.3:** Agent mode must output TOON (Token-Oriented Object Notation) on stdout — approximately 40% token savings over JSON.
- **FR-9.4:** Minimal default schemas: 3-4 fields in list output, not 10. Long-form content in detail views, not lists. Offer `--fields` flag for additional fields.
- **FR-9.5:** Content truncation: include truncated preview (500-1500 chars), show total size, suggest `--full` escape hatch only when content is actually truncated.
- **FR-9.6:** Pre-computed aggregates: include total count in list output, not just page size. Include derived status fields when the next step commonly involves checking related state.
- **FR-9.7:** Definitive empty states: when the answer is "nothing", say so explicitly with context. Make it clear the command succeeded.
- **FR-9.8:** Structured errors on stdout (not stderr). Include what went wrong and an actionable suggestion. Idempotent mutations (no error when desired state already exists, exit code 0). No interactive prompts — fail immediately with a clear error if a required value is missing.
- **FR-9.9:** Output channels: stdout = structured output (data, errors, suggestions); stderr = debug logging, progress indicators. Exit codes: 0 = success (including no-ops), 1 = error, 2 = usage error.
- **FR-9.10:** Session integrations: register into Claude Code (`~/.claude/settings.json` SessionStart hook), Codex (`~/.codex/hooks.json` SessionStart hook), OpenCode (`~/.config/opencode/plugins/` managed plugin). Explicit opt-in from a user-invoked setup command. Idempotent. Directory-scoped.
- **FR-9.11:** Installable Agent Skill as secondary discovery path. Generate `SKILL.md` from the same content as the no-args home view. Add `--check` build step to CI that fails if the committed skill is stale.

## Non-Functional Requirements

### NFR-1: Performance

- **NFR-1.1:** Detection must complete in under 100ms for projects with up to 1000 files.
- **NFR-1.2:** PATH scanning must complete in under 50ms.
- **NFR-1.3:** Security scanning must not add more than 30% overhead to the install time.
- **NFR-1.4:** The daemon must handle up to 10 concurrent background jobs without degradation.
- **NFR-1.5:** CLI response time (for non-async operations) must be under 50ms.

### NFR-2: Security

- **NFR-2.1:** apmw must never log secrets or credentials. Use the `secrecy` crate for secret handling and `zeroize` for secure memory clearing.
- **NFR-2.2:** apmw must validate all external inputs (package names, URLs, file paths).
- **NFR-2.3:** `cargo audit` must find no vulnerabilities in CI.
- **NFR-2.4:** The Dockerfile must use a non-root user (`rustuser`), multi-stage build, and HEALTHCHECK.
- **NFR-2.5:** Security scanning must run before every install — no bypass except explicit `--no-scan` flag.

### NFR-3: Usability

- **NFR-3.1:** Agent mode (TOON output, no prompts) is the default. Human mode is opt-in via `--human`.
- **NFR-3.2:** Error messages must follow the format `ERROR: <description> - <suggestion>`.
- **NFR-3.3:** The no-args output must show live content (detected manager, recent installs, active jobs), not a usage manual.
- **NFR-3.4:** Progress indicators must respect `--quiet` flag.

### NFR-4: Reliability

- **NFR-4.1:** The daemon must gracefully handle SIGINT (exit code 130) and SIGHUP (config reload).
- **NFR-4.2:** The daemon must auto-restart background jobs that fail due to transient errors.
- **NFR-4.3:** The audit log must be durable (flushed to disk before returning success to the caller).

### NFR-5: Maintainability

- **NFR-5.1:** Code must follow the rust-development-practices bundle: project-structure, cargo-config, async-patterns (tokio "full"), error-handling (thiserror + anyhow, no panics in libs), serde-serialization, cli-tool-standards, container-support, security-auditing, quality-gates, testing-strategy, rustfmt-clippy.
- **NFR-5.2:** All quality gates must pass: `cargo check`, `cargo test`, `cargo clippy` (no warnings), `cargo fmt --check`, `cargo doc`, `cargo build --release`, `cargo audit`.
- **NFR-5.3:** Module organization must be by feature/domain, not by file type.

### NFR-6: Portability

- **NFR-6.1:** apmw must compile and run on Linux, macOS, and Windows.
- **NFR-6.2:** MSRV (Minimum Supported Rust Version) is 1.70.
- **NFR-6.3:** Path handling must be cross-platform (use `std::path`, handle both forward and backward slashes).

### NFR-7: Telemetry Privacy

- **NFR-7.1:** Telemetry must never include personal identifiers, package names, file paths, URLs, or any user project content. Only categorical usage data (terminal type, command name, manager name, success/failure, duration, version).
- **NFR-7.2:** Telemetry must be opt-out via `--no-telemetry`, config (`telemetry = false`), or env var (`APMW_NO_TELEMETRY=1`).
- **NFR-7.3:** Telemetry collection must never block or fail the user's operation. If the telemetry endpoint is unreachable, data is silently dropped.
- **NFR-7.4:** The telemetry data schema and endpoint must be documented in the README so users know exactly what is collected and where it goes.
- **NFR-7.5:** A `--telemetry-preview` flag must print the telemetry payload that would be sent (without sending it) so users can audit the data.

### ADR-20260607001: CLI Tool Standards (v4.0.0, accepted)

Located at `~/p/gh/levonk/levonk-base-boilerplate/internal-docs/adr/adr-20260607001-cli-tool-standards.md`.

**Section 13 — Daemon Process Support** (lines 56-65):
> For long-running tasks (>30 seconds), provide daemon mode with job management. The implementation must support ALL of the following behaviors simultaneously:
> - Provide `--daemon` and `--no-daemon` flags as opposites
> - Auto-spawn daemon on first async operation (no flag required)
> - `--daemon` flag pre-launches daemon in background and waits for jobs
> - `--no-daemon` flag forces synchronous in-process operation (disables auto-spawning)
> - Include `--list-jobs` command to show background job status, with an optional job id list to filter results
> - Return the output from `--list-jobs` with job ID immediately when daemon performs the background operation
> - Include `--cancel-job <id>` command to cancel specific background jobs
> - Provide instructions for monitoring job progress
> - If daemon mode is not supported on the current platform, fall back to synchronous processing with a clear error message explaining the limitation if `--no-daemon` is not used. Suggest alternatives if `--daemon` is used. Allow a config variable to override this noisy behavior for non supported platforms.

**Sections 36-45 — Agent Mode Standards (AXI)** (lines 89-204):

- **Section 36 — Token-Efficient Output (TOON)**: Use TOON as the output format on stdout in agent mode. ~40% token savings over JSON. Convert to TOON at the output boundary — keep internal logic on JSON.
- **Section 37 — Minimal Default Schemas**: Default to the smallest schema that lets the agent decide what to do next: typically an identifier, a title, and a status. Default list schemas: 3-4 fields, not 10. Offer `--fields` flag.
- **Section 38 — Content Truncation**: Never omit large fields entirely — include a truncated preview. Show the total size. Suggest `--full` only when content is actually truncated. Choose a truncation limit that covers most use cases (500-1500 chars).
- **Section 39 — Pre-computed Aggregates**: Include the total count in list output, not just the page size. Include derived status fields when the next step almost always involves checking related state.
- **Section 40 — Definitive Empty States**: When the answer is "nothing", say so explicitly. Ambiguous empty output causes agents to re-run with different flags to verify.
- **Section 41 — Structured Errors and Exit Codes**: Idempotent mutations (no error when desired state already exists, exit code 0). Structured errors on stdout. No interactive prompts. stdout = structured output; stderr = debug logging. Exit codes: 0 = success, 1 = error, 2 = usage error.

## Risk Assessment

- **Priority:** P1
- **Effort:** L
- **Risk:** HIGH

### Key Risks

1. **AUR name collision**: An unrelated AUR package named `apmw` already exists (an apt-to-pacman translator by `mineleng@aur`). Arch Linux users who search for `apmw` will find the wrong package. **Mitigation**: Document the collision in the README. Use a different package name on AUR (e.g., `apmw-bin` or `apmw-rs`) or namespace it. The GitHub repo `levonk/apmw` is free to claim.

2. **Scope complexity**: The full vision includes 14 major features (detect, install, map, scan PATH, suggest, install missing, resolve versions, historyless clone, security scan, audit log, daemon, AI agent notification, AI agent hooks/MCP/Skills, multi-ecosystem release). This is a large project. **Mitigation**: Break into phased task stories. Phase 1 builds the foundation (detection, CLI, daemon skeleton). Later phases add features incrementally.

3. **Cross-platform daemon support**: Daemon mode may not work on all platforms (especially Windows). **Mitigation**: Implement platform fallback to synchronous mode with clear error messages (per ADR-20260607001 section 13). Use conditional compilation (`#[cfg(target_os = "...")]`).

4. **Scanner plugin ecosystem**: The two-phase scan pattern requires multiple security scanners. Initially, only a few scanners may be available. **Mitigation**: Start with `cargo audit` and npm audit. Add more scanners as plugins over time. The scanner plugin contract allows incremental addition.

5. **MCP protocol maturity**: The MCP (Model Context Protocol) is an emerging standard. The API may change. **Mitigation**: Abstract the MCP server behind a trait. Update the implementation as the protocol stabilizes.

6. **Multi-ecosystem release complexity**: Shipping to 9+ package ecosystems from one source requires significant CI/CD infrastructure. **Mitigation**: Mirror the existing `levonk-packages/packaging/` generator pattern. Start with cargo + npm + brew. Add ecosystems incrementally.

7. **Hard intercept vs soft convention for AI agent hooks**: The "force AI agents through apmw's install-on-use hook" requirement can be implemented as a hard intercept (PATH shim) or a soft convention (Skill/MCP). The hard intercept is more robust but more invasive. **Mitigation**: Implement both. The hard intercept is opt-in via `apmw --install --intercept`. The soft convention is the default via the installable Skill and MCP.

1. **PRD inside apmw repo vs levonk-packages**: The handoff document said to create the PRD in `levonk-packages/internal-docs/`, but the user has since decided apmw is its own standalone repo. The PRD is now at `~/p/gh/levonk/apmw/internal-docs/feature/2026/07/apmw/`. **Resolution**: PRD lives in the apmw repo. (Decided.)

2. **AUR name collision**: The unrelated `apmw` AUR package (apt-to-pacman translator) will confuse Arch users. Options: (a) use `apmw-bin` or `apmw-rs` on AUR, (b) namespace as `levonk-apmw`, (c) accept the collision and document it. **Recommendation**: (a) use `apmw-bin` on AUR — clear, conventional for binary packages, avoids confusion.

3. **Hard intercept vs soft convention for AI agent hook**: Should the "force AI agents through apmw's install-on-use hook" be a hard intercept (PATH shim that wraps pip/npm/cargo) or a soft convention (Skill/MCP that agents load)? **Recommendation**: Implement both. Hard intercept is opt-in via `apmw --install --intercept`. Soft convention is default via Skill + MCP. The hard intercept is more robust but invasive; the soft convention is less robust but non-invasive. Users choose their posture.

4. **Scanner plugin initial set**: Which security scanners should apmw ship with initially? **Recommendation**: Start with `cargo audit` (for Rust), `npm audit` (for Node), `pip-audit` / `safety` (for Python), `osv-scanner` (multi-ecosystem), and `trivy` / `grype` (for container images). Add more via the plugin contract over time.

5. **MCP server transport**: Should the MCP server use stdio, SSE, or WebSocket transport? **Recommendation**: stdio for local agent integration (Claude Code, Codex, OpenCode). SSE/WebSocket for remote integration if needed later.

6. **Daemon socket location**: Where should the daemon's local socket live? **Recommendation**: `${XDG_RUNTIME_DIR:-/tmp}/apmw/apmw.sock` on Linux/macOS. Named pipe on Windows.

7. **Telemetry endpoint**: Where should anonymized usage telemetry be sent? **Recommendation**: A levonk-owned endpoint (URL configurable in config). Start with a simple HTTP POST to a levonk-hosted ingestion service. Document the endpoint and data schema in the README.

8. **Governance spec caching**: apmw reads governance rules from the levonk-packages repo. Should it fetch the spec at runtime (network call) or cache it locally? **Recommendation**: Cache locally with a TTL (default 7 days). Fetch on first run, refresh in the background. Fall back to the cached copy if the network is unavailable. Allow `apmw governance refresh` to force a refresh.
