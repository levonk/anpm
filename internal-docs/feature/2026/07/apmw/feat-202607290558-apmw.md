# Product Requirements Document (PRD)

## Introduction / Overview

- **Feature name:** apmw (All Package Manager Wrapper)
- **Summary:** apmw is a Rust-based tool that abstracts every package installer into one intelligent surface. It detects the correct package manager for the current project, installs tools and dependencies with install-on-use semantics, maps ecosystems to canonical runners (pip to uv, npm/yarn/bun to pnpm, uvx to pnpm dlx), scans PATH before installing, resolves versions intelligently, creates historyless clones with AST indexing, runs security scanning before install, keeps an audit log, runs as a tokio daemon with background agents, notifies AI agents where to find package docs, exposes AI agent hooks/MCP/Skills, and ships as a multi-ecosystem release from one source.
- **Context:**
  - **Who:** Developers and AI agents (Claude Code, Codex, OpenCode) who interact with package managers across multiple ecosystems (Node, Python, Rust, Go, Debian, Brew, Nix, Snap, Yum, and more).
  - **Problem:** Every package manager has its own CLI, its own security posture, its own version resolution rules, and its own ad-hoc runner. Developers waste time context-switching between `pip`, `npm`, `cargo`, `brew`, `apt`, `nix`, and `go install`. AI agents have no enforced path for adding dependencies — they call whatever package manager they guess, bypassing security scanning and audit logging.
  - **Solution:** One tool that detects the right package manager, maps to canonical ecosystems, scans before installing, resolves versions intelligently, clones historylessly with AST indexing, and forces AI agents through a single install-on-use hook.
  - **Background:** The concept originated in the 2ndbrain vault note "APMW Tool Idea" (Obsidian, not in any git repo) and was refined in the 38KB research document "All Package Manager Wrapper Tool Landscape" containing Table 1 (project-detection attributes for 20+ package managers) and Table 2 (apmw command to per-package-manager command mapping with 200+ references). The PRD generation handoff document is at `/Users/micro/p/gh/levonk/levonk-packages/.agents/handoffs/2026/07/202607290407-apmw-prd-generation.md`.

## Goals

1. **Detect** the correct package manager for any project by scanning lockfiles, config files, and directory markers — delegating to the project-detection/project-adopter/project-configuration skills' logic.
2. **Install** tools and dependencies with install-on-use semantics, routing through devbox + rtk when no impossible barriers exist.
3. **Map ecosystems** to canonical runners: pip to uv, npm/yarn/bun/yarn2 to pnpm, uvx to pnpm dlx, and the canonical ad-hoc runner per ecosystem via `cli-tool-discovery.sh --runner`.
4. **Scan PATH** before installing to avoid duplicate installations.
5. **Suggest** better alternatives for the current use case (e.g., suggest uv when the user runs pip).
6. **Install missing tools** itself when needed, using the detected package manager.
7. **Resolve versions** intelligently: pinned version if locked; latest compatible with engine; latest if unspecified; latest minor if only major specified.
8. **Create historyless/branchless/tagless clones** of any package with `--depth 1 --single-branch --no-tags`, with indexed-AST search tools loaded and indexes created (CodeGraph/Graphify/GitNexus per the indexed-ast-tools decision tree). Add a local `.gitignore` so indexes, devbox.json, and AGENTS.md do not get pushed upstream.
9. **Run security scanning before install** (two-phase: scan all then install all), with option to update security databases first. Telemetry off for third-party packages; on or neutral for levonk-owned.
10. **Keep an audit log** in `${XDG_CACHE_HOME:-$HOME/.cache}/apmw/` recording: when, what was requested, what was done, whether the terminal was login/interactive, caller program, and which tools were used.
11. **Run as a Rust daemon** (tokio "full") with background agents doing clone/scan/index in the background; CLI reports status of clone/security-scan/install/indexing.
12. **Notify the user's AI agent** where to find docs for an installed package.
13. **Expose AI agent coding hooks, an MCP, and Skills** that force AI agents through apmw's install-on-use hook for adding dependencies and running tools.
14. **Ship as multi-ecosystem release** (npm/pnpm, PyPI/uv, brew, nix, devbox, apt, winget, apk, deb, rpm) from one source.

## User Stories

1. **As a developer**, I want to run `apmw install <package>` in any project directory and have apmw detect the right package manager, resolve the version, scan for security issues, and install — so I do not have to remember which package manager this project uses.

2. **As a developer**, I want apmw to scan my PATH before installing a tool and skip the installation if the tool is already available — so I avoid duplicate installations and wasted time.

3. **As a developer**, I want apmw to suggest better alternatives (e.g., uv instead of pip, pnpm instead of npm) — so I adopt the best tool for each ecosystem without researching manually.

4. **As a developer**, I want apmw to create a historyless clone of any package with AST indexing enabled — so I can search the code structurally without downloading git history or polluting the upstream repo with index files.

5. **As a developer**, I want apmw to run security scanning before installing anything — so I do not install packages with known vulnerabilities.

6. **As an AI agent** (Claude Code, Codex, OpenCode), I want apmw to expose an MCP server and installable Skills — so I can route all dependency additions and tool invocations through apmw's install-on-use hook without guessing the package manager.

7. **As an AI agent**, I want apmw to notify me where to find the docs for an installed package — so I can read the package's documentation before using its APIs.

8. **As a developer**, I want apmw to run as a daemon with background agents handling clone/scan/index — so long-running operations do not block my terminal.

9. **As a developer**, I want apmw to keep an audit log of every install/detect/clone operation — so I can review what was installed, when, and by which tool.

10. **As a DevOps engineer**, I want apmw to ship as multi-ecosystem packages (npm, PyPI, brew, nix, apt, winget, apk, deb, rpm) — so I can install it on any platform through the native package manager.

11. **As a developer**, I want apmw to resolve versions intelligently (pinned, engine-compatible, latest, latest-minor) — so I get the right version without manually specifying it every time.

12. **As an AI agent**, I want apmw to output in TOON format with minimal schemas and no interactive prompts — so I can parse the output efficiently and act on it without wasting tokens.

## Functional Requirements

### FR-1: Package Manager Detection

- **FR-1.1:** apmw must detect the package manager for the current project by scanning for lockfiles and config files (package.json, Cargo.toml, pyproject.toml, go.mod, Gemfile, pubspec.yaml, etc.).
- **FR-1.2:** Detection logic must delegate to the project-detection, project-adopter, and project-configuration skills' attribute-based detection. The 2ndbrain research Table 1 (at `/Users/micro/Documents/2ndbrain/2ndbrain/Work/01 OandO/Self Improvement/Want To Build/Digital/All Package Manager Wrapper/All Package Manager Wrapper Tool Landscape.md`) defines the detection attributes for 20+ package managers.
- **FR-1.3:** apmw must support detecting: npm, yarn, pnpm, pip, poetry, pipenv, pdm, conda, uv, maven, gradle, sbt, go, cargo, flutter, dart, dotnet, xcode, cocoapods, carthage, spm, cmake, ant, brew, nix, snap, yum, apt, winget, apk.
- **FR-1.4:** Detection must return the detected manager, the confidence level, and the evidence (which files triggered the detection).

### FR-2: Ecosystem Mapping

- **FR-2.1:** apmw must map ecosystems to canonical runners:
  - pip to uv
  - npm/yarn/bun/yarn2 to pnpm
  - uvx to pnpm dlx
  - The canonical ad-hoc runner per ecosystem via `cli-tool-discovery.sh --runner <ecosystem>` (python, node, rust, go)
- **FR-2.2:** When the user requests an install via a non-canonical manager (e.g., `pip install`), apmw must suggest the canonical alternative (e.g., `uv install`) and offer to use it.
- **FR-2.3:** The 2ndbrain research Table 2 (same file as FR-1.2) defines the apmw command to per-package-manager command mapping with 200+ references. apmw must implement this mapping table.

### FR-3: PATH Scanning

- **FR-3.1:** Before installing any tool, apmw must scan common PATH destinations to check if the tool is already installed.
- **FR-3.2:** PATH scanning must use the `cli-tool-discovery.sh` resolution flow: devbox-aware resolution (check `DEVBOX_SHELL` env first), then wrapper detection (mise, flox, direnv, nix), then 30+ standard PATH locations, then repo-root fallback dirs (`$REPO_ROOT/bin`, `scripts/`, `.local/bin`).
- **FR-3.3:** If the tool is found, apmw must report the path and skip installation.

### FR-4: Version Resolution

- **FR-4.1:** apmw must resolve versions using this priority:
  1. Pinned version if locked (from lockfile)
  2. Latest version compatible with the engine in use (e.g., Node version, mobile API tag)
  3. Latest if unspecified
  4. Latest minor if only a major version is specified
- **FR-4.2:** Version resolution must respect engine constraints from the project's config (e.g., `engines` field in package.json, `python-requires` in setup.py, `rust-version` in Cargo.toml).

### FR-5: Security Scanning (Two-Phase)

- **FR-5.1:** apmw must run security scanning BEFORE install, following the two-phase pattern from `executable_skill-install.sh`: scan all packages first, then install all packages.
- **FR-5.2:** Scanners must be loaded as plugins following the scanner contract:
  - `<name>_available` — can this scanner run?
  - `<name>_ensure` — prepare/install the scanner
  - `<name>_scan DIR` — scan a local directory, return 0=safe/1=risky/2=error
- **FR-5.3:** Risk aggregation must use OR semantics: if ANY scanner reports risky (return 1), the package is treated as risky. Scanner errors (return 2) are incomplete-scan warnings, not risk findings.
- **FR-5.4:** apmw must support `--on-risk` modes: `prompt` (ask in interactive TTY, error if not), `error` (abort immediately), `warn` (print warning, install anyway), `skip` (skip the risky package, continue).
- **FR-5.5:** apmw must support `--update-security-db` to refresh security databases before scanning.
- **FR-5.6:** Telemetry policy: telemetry off for third-party packages; on or neutral for levonk-owned packages. This mirrors the `executable_skill-install.sh` telemetry policy (lines 73-76).
- **FR-5.7:** Security posture must mirror the `npmrc.tmpl` settings: `audit=true`, `audit-level=high`, `engine-strict=true`, `frozen-lockfile=true`, `save-exact=true`, `provenance=true`.

### FR-6: Historyless Clone with AST Indexing

- **FR-6.1:** apmw must create historyless, branchless, tagless clones using `git clone --depth 1 --single-branch --no-tags`.
- **FR-6.2:** After cloning, apmw must add a local `.gitignore` that excludes: AST index files, `devbox.json`, `AGENTS.md` — so these do not get pushed upstream.
- **FR-6.3:** apmw must load the appropriate indexed-AST search tool and create indexes, following the indexed-ast-tools decision tree:
  1. Project < 20 files? Skip indexing (agent can read everything directly).
  2. Need to link non-code knowledge (PDFs, docs, video, images) to code? Use Graphify (MIT, multimodal).
  3. Work across multiple repos/services? Use GitNexus (PolyForm Noncommercial — procure commercial license for business use).
  4. Need zero-maintenance + dynamic dispatch tracing? Use CodeGraph (MIT, auto-sync, single tool) — **default**.
  5. Power-user structural queries on a single repo? Use GitNexus (17 specialized MCP tools).
- **FR-6.4:** CodeGraph is the default for single-project zero-maintenance workflows.

### FR-7: Audit Log

- **FR-7.1:** apmw must keep an audit log in `${XDG_CACHE_HOME:-$HOME/.cache}/apmw/`.
- **FR-7.2:** Each log entry must record: timestamp (when), what was requested, what was done, whether the terminal was login/interactive, the caller program (if any), and which tools were used to install/run.
- **FR-7.3:** The audit log must be append-only with configurable retention period (per ADR-20260607001 section 34).
- **FR-7.4:** apmw must support an export command for external analysis of the audit log.

### FR-8: Daemon + CLI Service Model

- **FR-8.1:** apmw must run as a long-running Rust daemon (tokio "full") for background jobs (clone, scan, index).
- **FR-8.2:** The CLI is a thin client over a local socket that communicates with the daemon.
- **FR-8.3:** apmw must support `--daemon` (pre-launch daemon in background and wait for jobs), `--no-daemon` (force synchronous in-process operation), `--list-jobs` (show background job status, returns job ID immediately), `--cancel-job <id>` (cancel specific background jobs).
- **FR-8.4:** Auto-spawn daemon on first async operation (no flag required).
- **FR-8.5:** If daemon mode is not supported on the current platform, fall back to synchronous processing with a clear error message. Suggest alternatives if `--daemon` is used. Allow a config variable to override this noisy behavior for unsupported platforms.
- **FR-8.6:** This follows ADR-20260607001 section 13 exactly.

### FR-9: AXI Agent Mode

- **FR-9.1:** Agent mode is the DEFAULT (per ADR-20260607001 sections 36-45). No flags required.
- **FR-9.2:** Human mode triggered via `--human` flag, `--interactive` flag, TUI mode, or auto-detection when TTY is present and no agent session is detected.
- **FR-9.3:** Agent mode must output TOON (Token-Oriented Object Notation) on stdout — approximately 40% token savings over JSON.
- **FR-9.4:** Minimal default schemas: 3-4 fields in list output, not 10. Long-form content in detail views, not lists. Offer `--fields` flag for additional fields.
- **FR-9.5:** Content truncation: include truncated preview (500-1500 chars), show total size, suggest `--full` escape hatch only when content is actually truncated.
- **FR-9.6:** Pre-computed aggregates: include total count in list output, not just page size. Include derived status fields when the next step commonly involves checking related state.
- **FR-9.7:** Definitive empty states: when the answer is "nothing", say so explicitly with context. Make it clear the command succeeded.
- **FR-9.8:** Structured errors on stdout (not stderr). Include what went wrong and an actionable suggestion. Idempotent mutations (no error when desired state already exists, exit code 0). No interactive prompts — fail immediately with a clear error if a required value is missing.
- **FR-9.9:** Output channels: stdout = structured output (data, errors, suggestions); stderr = debug logging, progress indicators. Exit codes: 0 = success (including no-ops), 1 = error, 2 = usage error.
- **FR-9.10:** Session integrations: register into Claude Code (`~/.claude/settings.json` SessionStart hook), Codex (`~/.codex/hooks.json` SessionStart hook), OpenCode (`~/.config/opencode/plugins/` managed plugin). Explicit opt-in from a user-invoked setup command. Idempotent. Directory-scoped.
- **FR-9.11:** Installable Agent Skill as secondary discovery path. Generate `SKILL.md` from the same content as the no-args home view. Add `--check` build step to CI that fails if the committed skill is stale.
- **FR-9.12:** Content-first no-args: running `apmw` with no arguments shows the most relevant live content (current project's detected manager, recent installs, active background jobs), not a usage manual.
- **FR-9.13:** Contextual disclosure: include 2-4 next steps that follow logically from the current output, as complete commands in a `help[]` array.

### FR-10: AI Agent Hooks, MCP, and Skills

- **FR-10.1:** apmw must expose an MCP (Model Context Protocol) server that AI agents connect to for install/detect/scan operations.
- **FR-10.2:** apmw must expose AI agent coding hooks that force AI agents through apmw's install-on-use hook for adding dependencies and running tools. This includes both:
  - **Hard intercept**: PATH shim that wraps package manager binaries (e.g., `pip`, `npm`, `cargo`) so any invocation routes through apmw.
  - **Soft convention**: Installable Agent Skill that agents load, which instructs them to use `apmw install` instead of calling package managers directly.
- **FR-10.3:** apmw must expose installable Skills (following the Agent Skills format at agentskills.io) as a secondary discovery path.

### FR-11: AI Agent Docs Notification

- **FR-11.1:** After installing a package, apmw must notify the user's AI agent where to find the docs for that package.
- **FR-11.2:** The notification must include: the package name, the docs URL (if available from the package metadata), and the local path to any README/docs files installed with the package.

### FR-12: Multi-Ecosystem Release

- **FR-12.1:** apmw must ship as multi-ecosystem packages from one source: npm/pnpm, PyPI/uv, brew, nix, devbox, apt, winget, apk, deb, rpm.
- **FR-12.2:** The release pipeline must mirror the `levonk-packages/packaging/` generator pattern (alpine/debian/fedora/arch/brew/mise generators).
- **FR-12.3:** The Rust binary is the single source; each ecosystem package wraps the pre-built binary.

### FR-13: CLI Standards Compliance

- **FR-13.1:** apmw must comply with all applicable sections of ADR-20260607001: standard arguments (`--help`, `--version`, `--usage`), configuration precedence (CLI args > env vars > local project config > user config (XDG) > system config > defaults), config file initialization, `--install`/`--uninstall`, input and globbing, output discipline (stdout for results, stderr for logs, `--json` mode, `--color=auto|always|never`, `NO_COLOR`), logging modes (`--verbose`, `--quiet`, `--debug`), signals and exit codes, TUI mode, dry-run, confirmation prompts, progress indicators, error formatting, shell completion, man pages, pager integration, subcommand organization, config validation, terminal size awareness, environment variable naming (`APMW_*`), cross-platform path handling, credential/secret handling, resource limits, collection vs processing separation, config auto-migration, structured logging, signal-based config reload, health check for containers, privacy mode, audit logging with retention, legacy deprecation policy.

## Non-Functional Requirements

### NFR-1: Performance

- **NFR-1.1:** Detection must complete in under 100ms for projects with up to 1000 files.
- **NFR-1.2:** PATH scanning must complete in under 50ms.
- **NFR-1.3:** Security scanning must not add more than 30% overhead to the install time.
- **NFR-1.4:** The daemon must handle up to 10 concurrent background jobs without degradation.
- **NFR-1.5:** CLI response time (for non-async operations) must be under 50ms.

### NFR-2: Security

- **NFR-2.1:** apmw must never log secrets or credentials. Use the `secrecy` crate for secret handling and `zeroize` for secure memory clearing.
- **NFR-2.2:** apmw must validate all external inputs (package names, URLs, file paths).
- **NFR-2.3:** `cargo audit` must find no vulnerabilities in CI.
- **NFR-2.4:** The Dockerfile must use a non-root user (`rustuser`), multi-stage build, and HEALTHCHECK.
- **NFR-2.5:** Security scanning must run before every install — no bypass except explicit `--no-scan` flag.

### NFR-3: Usability

- **NFR-3.1:** Agent mode (TOON output, no prompts) is the default. Human mode is opt-in via `--human`.
- **NFR-3.2:** Error messages must follow the format `ERROR: <description> - <suggestion>`.
- **NFR-3.3:** The no-args output must show live content (detected manager, recent installs, active jobs), not a usage manual.
- **NFR-3.4:** Progress indicators must respect `--quiet` flag.

### NFR-4: Reliability

- **NFR-4.1:** The daemon must gracefully handle SIGINT (exit code 130) and SIGHUP (config reload).
- **NFR-4.2:** The daemon must auto-restart background jobs that fail due to transient errors.
- **NFR-4.3:** The audit log must be durable (flushed to disk before returning success to the caller).

### NFR-5: Maintainability

- **NFR-5.1:** Code must follow the rust-development-practices bundle: project-structure, cargo-config, async-patterns (tokio "full"), error-handling (thiserror + anyhow, no panics in libs), serde-serialization, cli-tool-standards, container-support, security-auditing, quality-gates, testing-strategy, rustfmt-clippy.
- **NFR-5.2:** All quality gates must pass: `cargo check`, `cargo test`, `cargo clippy` (no warnings), `cargo fmt --check`, `cargo doc`, `cargo build --release`, `cargo audit`.
- **NFR-5.3:** Module organization must be by feature/domain, not by file type.

### NFR-6: Portability

- **NFR-6.1:** apmw must compile and run on Linux, macOS, and Windows.
- **NFR-6.2:** MSRV (Minimum Supported Rust Version) is 1.70.
- **NFR-6.3:** Path handling must be cross-platform (use `std::path`, handle both forward and backward slashes).

### ADR-20260607001: CLI Tool Standards (v4.0.0, accepted)

Located at `/Users/micro/p/gh/levonk/levonk-base-boilerplate/internal-docs/adr/adr-20260607001-cli-tool-standards.md`.

**Section 13 — Daemon Process Support** (lines 56-65):
> For long-running tasks (>30 seconds), provide daemon mode with job management. The implementation must support ALL of the following behaviors simultaneously:
> - Provide `--daemon` and `--no-daemon` flags as opposites
> - Auto-spawn daemon on first async operation (no flag required)
> - `--daemon` flag pre-launches daemon in background and waits for jobs
> - `--no-daemon` flag forces synchronous in-process operation (disables auto-spawning)
> - Include `--list-jobs` command to show background job status, with an optional job id list to filter results
> - Return the output from `--list-jobs` with job ID immediately when daemon performs the background operation
> - Include `--cancel-job <id>` command to cancel specific background jobs
> - Provide instructions for monitoring job progress
> - If daemon mode is not supported on the current platform, fall back to synchronous processing with a clear error message explaining the limitation if `--no-daemon` is not used. Suggest alternatives if `--daemon` is used. Allow a config variable to override this noisy behavior for non supported platforms.

**Sections 36-45 — Agent Mode Standards (AXI)** (lines 89-204):

- **Section 36 — Token-Efficient Output (TOON)**: Use TOON as the output format on stdout in agent mode. ~40% token savings over JSON. Convert to TOON at the output boundary — keep internal logic on JSON.
- **Section 37 — Minimal Default Schemas**: Default to the smallest schema that lets the agent decide what to do next: typically an identifier, a title, and a status. Default list schemas: 3-4 fields, not 10. Offer `--fields` flag.
- **Section 38 — Content Truncation**: Never omit large fields entirely — include a truncated preview. Show the total size. Suggest `--full` only when content is actually truncated. Choose a truncation limit that covers most use cases (500-1500 chars).
- **Section 39 — Pre-computed Aggregates**: Include the total count in list output, not just the page size. Include derived status fields when the next step almost always involves checking related state.
- **Section 40 — Definitive Empty States**: When the answer is "nothing", say so explicitly. Ambiguous empty output causes agents to re-run with different flags to verify.
- **Section 41 — Structured Errors and Exit Codes**: Idempotent mutations (no error when desired state already exists, exit code 0). Structured errors on stdout. No interactive prompts. stdout = structured output; stderr = debug logging. Exit codes: 0 = success, 1 = error, 2 = usage error.
- **Section 42 — Ambient Context via Session Integrations**: Register into Claude Code (`~/.claude/settings.json` SessionStart hook), Codex (`~/.codex/hooks.json` SessionStart hook), OpenCode (`~/.config/opencode/plugins/` managed plugin). Explicit opt-in. Idempotent. Directory-scoped. Token-budget-aware.
- **Section 43 — Installable Agent Skill (Secondary)**: Generate `SKILL.md` from the same content as the no-args home view. Add `--check` build step to CI. Strip live state. Non-interactive commands. Trigger-shaped frontmatter.
- **Section 44 — Content First**: Running the CLI with no arguments should show the most relevant live content, not a usage manual.
- **Section 45 — Contextual Disclosure**: Include 2-4 next steps that follow logically from the current output, as complete commands in a `help[]` array.

### skill-install.sh Two-Phase Scan Pattern

Located at `/Users/micro/p/gh/levonk/dotfiles/home/current/dot_local/bin/executable_skill-install.sh`.

**Two-phase scan-all-then-install-all** (lines 12-14):
> Before installing, each skill is scanned with multiple security scanners for security risks. All skills are scanned before any are installed (two-phase: scan all -> install all).

**Scanner plugin contract** (lines 19-23):
> Each scanner plugin follows a contract (see scanners/common.sh):
>   `<name>_available` — can this scanner run?
>   `<name>_ensure` — prepare/install the scanner
>   `<name>_scan DIR` — scan a local directory, return 0=safe/1=risky/2=error

> Risk aggregation: OR semantics. If ANY scanner reports risky (return 1), the skill is treated as risky. Scanner errors (return 2) are incomplete-scan warnings, not risk findings.

**Shallow clone then scan** (lines 28-31):
> Flow: each skill repo is shallow-cloned (--depth 1 --single-branch --no-tags) to a temp directory, then all enabled scanners run against that directory.

**`--on-risk` modes** (lines 55-59):
> `--on-risk=MODE` Behavior when any scanner flags a skill as risky:
>   prompt — ask in interactive TTY, error if not (default)
>   error — abort immediately
>   warn — print warning, install anyway
>   skip — skip the risky skill, continue

**Telemetry policy** (lines 73-76):
> Telemetry policy: the `pnpm dlx skills` CLI sends telemetry unless DISABLE_TELEMETRY or DO_NOT_TRACK is set in the environment. We allow telemetry for levonk-owned skills (our own distribution) and disable it for everyone else's skills to avoid leaking usage data to third parties.

### cli-tool-discovery.sh --runner Contract

Located at `/Users/micro/p/gh/levonk/skills-src/build/current/includes/cli-tool-discovery.md`.

**Purpose** (lines 7-12):
> Before concluding a CLI tool is unavailable, run `cli-tool-discovery.sh`. Never give up on the first `command -v` failure.

**`--runner` mode** (lines 14-18):
> For ad-hoc package execution (e.g. `uvx`, `pnpm dlx`, `cargo binstall`, `go install`), use `--runner <ecosystem>` instead of resolving the binary and hardcoding the invocation. The runner mode is the single source of truth for "how do I invoke an ad-hoc command in ecosystem X?" — it pairs the binary resolution with the canonical invocation pattern from the tech-stack table.

**Usage** (lines 33-43):
```bash
# Resolve only — print where the tool is or how to run it
cli-tool-discovery.sh <tool-name>          # text output
cli-tool-discovery.sh <tool-name> --json   # JSON output (for scripts)

# Resolve and exec — runs the tool through the right wrapper/path, never returns
cli-tool-discovery.sh -- <tool-name> [args...]

# Resolve the ad-hoc runner for an ecosystem (JSON only)
cli-tool-discovery.sh --runner <python|node|rust|go>
```

**Devbox-aware resolution flow** (lines 57-74):
> The devbox shell environment variable (`DEVBOX_SHELL` or `IN_DEVBOX_SHELL`) is checked first, before any other resolution. If we're already inside a `devbox shell`, devbox-managed binaries are on `PATH` and no wrapper detection is needed (mise/flox/direnv/nix are skipped entirely).

**Output modes** (lines 46-52):
| Output | Meaning | Action |
|--------|---------|--------|
| `FOUND: <path>` | Tool found at a specific path | Use that path directly |
| `WRAPPER: <wrapper-cmd>` | Tool is inside an environment wrapper | Run via the wrapper |
| `NOT_FOUND: <tool>` | Tool not found anywhere | Install it |

### Key Risks

1. **AUR name collision**: An unrelated AUR package named `apmw` already exists (an apt-to-pacman translator by `mineleng@aur`). Arch Linux users who search for `apmw` will find the wrong package. **Mitigation**: Document the collision in the README. Use a different package name on AUR (e.g., `apmw-bin` or `apmw-rs`) or namespace it. The GitHub repo `levonk/apmw` is free to claim.

2. **Scope complexity**: The full vision includes 14 major features (detect, install, map, scan PATH, suggest, install missing, resolve versions, historyless clone, security scan, audit log, daemon, AI agent notification, AI agent hooks/MCP/Skills, multi-ecosystem release). This is a large project. **Mitigation**: Break into phased task stories. Phase 1 builds the foundation (detection, CLI, daemon skeleton). Later phases add features incrementally.

3. **Cross-platform daemon support**: Daemon mode may not work on all platforms (especially Windows). **Mitigation**: Implement platform fallback to synchronous mode with clear error messages (per ADR-20260607001 section 13). Use conditional compilation (`#[cfg(target_os = "...")]`).

4. **Scanner plugin ecosystem**: The two-phase scan pattern requires multiple security scanners. Initially, only a few scanners may be available. **Mitigation**: Start with `cargo audit` and npm audit. Add more scanners as plugins over time. The scanner plugin contract allows incremental addition.

5. **MCP protocol maturity**: The MCP (Model Context Protocol) is an emerging standard. The API may change. **Mitigation**: Abstract the MCP server behind a trait. Update the implementation as the protocol stabilizes.

6. **Multi-ecosystem release complexity**: Shipping to 9+ package ecosystems from one source requires significant CI/CD infrastructure. **Mitigation**: Mirror the existing `levonk-packages/packaging/` generator pattern. Start with cargo + npm + brew. Add ecosystems incrementally.

7. **Hard intercept vs soft convention for AI agent hooks**: The "force AI agents through apmw's install-on-use hook" requirement can be implemented as a hard intercept (PATH shim) or a soft convention (Skill/MCP). The hard intercept is more robust but more invasive. **Mitigation**: Implement both. The hard intercept is opt-in via `apmw --install --intercept`. The soft convention is the default via the installable Skill and MCP.
